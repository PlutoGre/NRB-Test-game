# 10 永久活动：All Blue 与幸运转盘

本批依次接入 All Blue 和幸运转盘，复用参考 APK 的两套 CCB 界面及美术，采用本地服务端定义的概率和固定奖池。两个入口在“冒险（活动）”页永久显示，无等级门槛，不依赖旧活动排期或参考 APK 的在线服务器。

**2026-11-03 已重新编译服务端覆盖包、Android 和 Web，在雷电及局域网浏览器完成真实登录、抽取、兑换、累计领奖、传书领取和服务端重启保存验证；当前本机 `outputs` 已更新。实测范围、修复及产物校验见[永久活动安卓与网页验证记录](../reference/永久活动安卓与网页验证记录.md)。iOS 本次未构建或验证。**

## 默认玩法

| 项目 | All Blue | 幸运转盘 |
|---|---|---|
| 免费机会 | 每天 1 次单次探索 | 每天 1 次抽取 |
| 普通费用 | 30 钻石/次 | 20 钻石/次 |
| 批量操作 | 十次探索 270 钻石，不消耗当天免费机会 | 本批按单次抽取 |
| 积分 | 每次探索 10 分，十次获得 100 分 | 每次抽取 1 分，重复格也计分 |
| 兑换 | 独立积分商店 | 独立积分商店 |
| 附加规则 | 宝库显示最近一次探索或兑换奖励；岛屿按钮可查看固定奖池 | 本轮首次命中奖励格获得对应奖励；再次命中同格获得 1000 贝里保底 |
| 重置 | 无需重置 | 30 钻石重置本轮收集格；集齐 8 格后免费重置，积分和累计次数保留 |
| 累计奖励 | 无 | 累计 10、30、100 次可分别领取潜能药剂×10、霸王色缠绕×1、大和×1，每档每角色一次 |

免费次数按北京时间每天零点刷新。两种活动的免费机会、积分、抽取次数和兑换状态互相独立。

中奖、兑换和累计领取的奖励均发送至当前角色的传书，页面结果窗口提供“前往传书”。**领取传书后，资产才进入背包或卡牌、装备、奥义列表。** 重复完整卡沿用原有领取规则转换为影子；系统钻石不会增加累计充值或 VIP。

## 如何应用本批更新

1. 先完成必要的[服务端数据备份](../服务端数据备份与迁移.md)，再停止当前实例。
2. 更新仓库代码，然后运行根目录 `启动服务.cmd`。首次应用会生成新的 Java 覆盖包、追加活动资源、更新资源清单，默认资源版本升至 **1.79.0**；已配置的更高版本保留。
3. 重新生成 Android、iOS 或 Web 客户端。三端使用同一个 C++ 活动实现及同一份资源，旧原生库或旧 WebAssembly 不会因资源热更新而增加新代码。
4. 重新进入游戏的冒险页，查看 All Blue 和幸运转盘。Android/雷电继续按[客户端打包流程](../客户端打包流程.md)选择对应包；Web 按[网页客户端流程](../网页客户端流程.md)构建并启动。

常规克隆、部署和打包不需要原 APK，也不需要再次执行资源导入脚本。

已有服务仍运行时，启动脚本会提示永久活动更新待应用，需停止后再启动。它不会在玩家在线时替换游戏服和内存模板。更新前的文件保存在 `runtime/server/private/catalog-backups/`；完成标记为 `runtime/server/private/permanent-activities-v1.json`，重复启动不会重复追加活动表行。

## 修改奖池、概率与费用

- 新部署默认值：`server/config/xml/permanentActivities.json`。
- 已部署实例：`runtime/server/server/xml/permanentActivities.json`。使用自定义运行目录时，路径相应替换。

停止游戏服后编辑，再重新启动即可载入。当前实例的文件一旦存在，仓库更新会保留它；修改仓库默认值不会覆盖既有实例的自定义配置。

`rewards` 保持 8 项，每项包括：

| 字段 | 含义 |
|---|---|
| `key` | 原管理目录的物品键，如 `property:1002`、`tool:1502001`、`skill:88`、`equip:107`、`card:249` |
| `name`、`icon` | 活动展示名称和客户端已有资源路径 |
| `count` | 单次奖励数量，不能超过管理目录中该物品的数量上限 |
| `weight` | 正整数权重；实际概率等于本项权重除以所有权重总和 |

`allBlue` 和 `fortuneWheel` 分别配置免费次数、单次费用、积分和商店。`tenCost` 为 All Blue 十次费用，`resetCost` 为转盘重置费用，`duplicateReward` 为转盘重复格保底。`shop[].reward`、`milestones[].reward` 使用奖池下标 **0～7**；商品及累计奖励的 `id` 为不重复的 **1～99**。

入口编号 `9001`、`9002` 不应修改。累计领取按奖励 `id` 保存，修改既有 ID 对应的奖品不会重置已领取记录。新增客户端没有的物品或图片时，还需同步模板、资源、版本并重新打包。

配置中的物品不存在、权重无效或数量超限会阻止活动初始化，应先修正日志指出的配置再启动。

## 保存、重试与迁移

| 位置 | 保存内容 |
|---|---|
| `dzm.nrb_permanent_activity` | 以角色 ID 和活动名为主键保存积分、免费使用日期/次数、转盘格、累计领取记录及最近奖励 |
| `dzm.nrb_permanent_activity_requests` | 每次付费、兑换、重置和累计领取的幂等回执 |
| 原 `player`、`rewards` 表 | 钻石余额及待领取的实际奖励传书 |

扣费、活动状态、回执和奖励传书在同一个数据库事务提交；定时保存与活动消费使用同一角色锁。提交确认中断时，先从数据库恢复余额，再继续操作或保存。

客户端发送前保存待确认操作编号。断线或重新进入活动后使用原编号核对，成功或明确拒绝后才清除。切换账号、区服或活动不会共用待确认操作。完整数据库备份包含两张新增表，迁移时应与账号、角色及传书一起恢复。
