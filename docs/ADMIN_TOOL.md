# Windows 游戏管理工具

## 直接使用

工具是项目根目录的 **`NRB游戏管理.exe`**，为普通 Windows 10/11 的 .NET Framework 桌面程序。无需安装 Python、Java、Android 环境或额外的 .NET SDK；程序本身使用 Windows 自带的 .NET Framework 4.x，按 AnyCPU 生成。服务端仍按原部署要求运行在 Windows x64 上。

**工具与服务端在同一台电脑使用**。任意目录 clone 本仓库后，按以下顺序操作：

1. 双击 **启动服务.cmd**，等待部署/启动成功。
2. 双击 **NRB游戏管理.exe**。默认自动定位 EXE 所在目录的 `runtime/server`。
3. 状态显示“服务端就绪”后，使用账号 **`op_root`**、密码 **`hy1212`** 登录。
4. 按分类或名称、模板 ID 搜索物品，填写数量，点击“加入发放清单”。
5. 选择“指定游戏名”，输入完整角色名，也可点击“查找角色”选择；或选择“全服现有角色（含离线）”。
6. 填写传书标题和说明，点击“预览并发送”，核对接收范围、角色数和物品后确认。
7. 玩家在游戏内 **传书** 中领取。在线角色会收到列表更新；离线角色下次登录后可领取，若原页面没有刷新可退出传书页再打开。

投递不需要等待定时落库周期。当前电脑已实测在线推送和离线登录领取，通常几秒内即可看到。若显示发送失败或结果未确认，应先查询批次，等待更久或反复重登不会修复未入库的发放。

“全服”指预览时数据库中已经创建的全部角色，不包含以后新建的角色，也不包含尚未创建游戏角色的平台账号。单人模式按完整游戏名精确匹配；找不到或出现重名会拒绝发放。

### 已经部署过的电脑

先在项目根目录 `git pull`，确认近期游戏进度已经保存，再依次双击 **停止服务.cmd → 启动服务.cmd**。启动工具会自动安装配套管理模块，保留原数据库、运行目录及已有游戏端口。无需重装客户端，也不需要手动重新编译服务端。

只更新仓库而保持旧游戏进程运行，不会加载新接口。启动输出会提示 `Local administration update pending`，此时按上面的停服/启动步骤处理。不要通过重新导入 SQL 解决接口问题。

### 自定义目录

若原部署使用了 `-InstallDir`，仍使用相同参数启动服务；在管理工具中点击“选择运行目录”，选择包含 `.onepiece-server.json` 的实际服务运行目录。也可以通过快捷方式参数指定：

```powershell
& '.\NRB游戏管理.exe' --install-dir 'D:\自己的运行目录'
```

上述绝对路径仅是参数示例，程序没有固定盘符；复制 EXE 到其他目录后也可通过界面选择现有部署。工具不是远程连接程序，不能仅复制到另一台未部署服务的电脑来管理原电脑上的服务器。

## 已集成的物品

目录读取的是 **实际运行服 XML 模板**，名称来自本仓库当前发布资源表。按当前源码模板统计，共 **5,235** 个发放条目：

| 分类 | 数量 | 发放含义 |
|---|---:|---|
| 货币/经验 | 3 | 系统钻石、贝里、海贼团经验 |
| 完整卡牌 | 2,324 | 新卡附带天生奥义；已拥有的卡牌按原品质规则转为影子 |
| 卡牌影子 | 2,324 | 对应每个卡牌模板 |
| 装备 | 91 | 武器、防具、饰品；按填写数量创建实际装备实例 |
| 奥义 | 77 | 按填写数量创建实际奥义实例 |
| 背包道具 | 94 | 服务端 `tools.xml` 中的药剂、海鲜饭、箱子、钥匙、礼包、宝石等 |
| 奥义残章 | 322 | `skillBookConfig.xml` 中的残章，进入残章页面查看 |

卡牌清单包括 NPC 和隐藏模板，并不等于 2,324 张独立可抽取角色。客户端表有名称而运行服没有加载的道具不会出现在目录中。修改服务端模板后，按原流程部署并重启；新增 ID 没有名称资源时会显示类别和 ID，可重新生成管理包更新名称。

系统钻石走系统赠送余额，不增加累计充值、充值钻石或 VIP。经验沿用 `UserPropertyServices.changeProperty()` 的处理，不是直接设置角色等级。

每批最多 20 种物品，每名角色最多创建 100 个卡牌/装备/奥义实例。完整卡牌单项最多 10；装备/奥义单项最多 100；残章最多 1,000；背包道具/影子最多 1,000,000；货币/经验最多 100,000,000。领取时还会检查旧客户端的整数上限。

旧数据库单封传书附件字段只有 255 字符，工具会按实际序列化长度拆信。传书沿用游戏现有清理规则，请及时领取；当前清理代码可能删除超过约三天的未领取奖励。

## 发放记录与异常处理

“发放记录”显示最近 50 个批次，包括已入库与已取消记录。**传书已入库不代表玩家已领取**。

- 发奖批次号与本批全部传书在同一数据库事务中保存；同一批次号重试不会重新创建传书。
- 客户端发送前把待确认批次保存在本机用户目录。网络超时、窗口关闭后重新登录，先点击“查询待确认批次”。
- 已提交时显示原结果；尚未查到时可按原批次重新预览/重试。不要手工删待确认记录再建立新批次。
- “取消未完成批次”会保存取消记录，阻止迟到请求发放；若原批次已经提交，会返回已提交结果，**不会撤销已经发出的传书**。

### 旧版发送后一直没有收到

2026-11-02 已复现并修复：旧 Hibernate 不能自动映射批次表 `MEDIUMTEXT` 列返回的 JDBC 类型 `-1`，导致发送前查询批次就失败，未创建任何传书。查询批次和查看历史均已改成显式字符串映射，无需重建数据库。

更新仓库后，**先关闭管理工具，再停止/启动服务端，然后打开新版 EXE**。原工具留下待确认批次时，先点“查询待确认批次”：已提交就保留原结果；未查到记录时，使用“预览并重试原批次”。不要另建同内容的新批次来替代查询。

界面改为按文字和字体自适应高度，标题、说明和目录输入框随窗口伸缩，长文本换行，类别/ID 列自动调整宽度。窗口较小时通过滚动区域访问完整表单，底部结果框支持滚动、复制完整批次号。

日志和数据位置：

| 位置 | 内容 |
|---|---|
| 运行目录 `logs/game.stdout.log`、`logs/game.stderr.log` 及游戏原日志目录 | 管理接口初始化、发放、领取错误 |
| 数据库 `nrb_admin_batches` | 持久化批次审计和防重复记录 |
| 数据库 `rewards` | 角色实际领取的传书 |
| `%LOCALAPPDATA%\NRBGameAdmin\admin.log` | 桌面工具错误日志，不保存密码或令牌 |
| 同一目录 `pending-<实例ID>.json` | 待确认批次和原始发放内容，不保存登录密码 |

领取工具传书时，先把该传书标记为“处理中”，再复用原游戏方法创建资产，成功后保存受影响的资产和已领取状态。原游戏实例创建方法会自行提交，因此这不是覆盖所有创建步骤的单一事务：中途进程退出或数据库异常可能留下部分资产和处理中记录。此时按角色、传书 ID 检查日志与数据库后处理，不能直接改回未领取再重发。普通旧传书继续走原领取逻辑。

## 部署与代码结构

- EXE 只连接 `127.0.0.1`，管理端口默认从 `18090` 开始选择空闲端口，写入本次部署记录；不会开放到局域网或 Quick Tunnel。
- 接口在游戏初始化、数据库可读及主循环能执行任务后才可登录；不是只检测端口是否有人监听。
- 登录由服务端验证，令牌有效期 30 分钟；连续错误登录会短暂限流。固定账号密码仅用于这个个人测试项目。
- 原 `DZM.jar` 保留，启动时通过 `NRBAdminServer.jar;DZM.jar` 类路径先加载管理模块和必要的业务适配类，原 GM 开关继续关闭。
- 传书对旧客户端显示残章所属奥义的名称，领取仍按真实残章 ID 入库；无需为此修改 APK。
- 此配套包也包含上次“连续登录”活动的 Java 修复，更新后停服/启动会一并加载；原 JAR 文件本身没有被覆盖。
- 管理包与原 JAR 的 SHA-256 写在 `deployment/admin/artifacts.json`。自定义修改原 JAR 后，应重新生成配套包，避免使用不匹配的业务类。
